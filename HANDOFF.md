## 1. What lorre-blocks is

A **design-token system + component registry** in the spirit of Radix Themes (token/theme
architecture) with **shadcn-style distribution**: nothing is installed from `node_modules`.
A CLI copies real component source *into the consumer's project*, so they own and can edit
every file.

```bash
npx lorre-blocks init          # writes theme CSS + components.json + lib/utils.ts
npx lorre-blocks add button    # copies button.tsx into the project + installs its deps
```

Three ideas hold the whole thing together:

1. **A theme is data, never code.** A theme is a set of token values (5 OKLCH color seeds +
   radius/shadow/motion/typography). Components only reference semantic tokens
   (`bg-primary`, `border-border`, `rounded-(--button-radius)`). Swapping a theme is one
   command and touches **zero** component files. If you ever need to fork a component to
   make a theme work, the *tokens* are wrong — fix the tokens.
2. **One engine, three consumers.** `packages/tokens` is pure TypeScript with zero Node
   dependencies, so the exact same code generates CSS in the build, in the CLI (bundled),
   and in the browser (the `/themes` Theme Studio page). The acceptance bar for anything
   token-related: **Studio-exported CSS must be byte-identical to CLI-injected CSS** for the
   same theme definition. There is a test that enforces it.
3. **Agent-first.** Every CLI command takes `--json` (one JSON doc on stdout, never
   prompts). `lorre.theme.json` is the human↔agent contract for custom themes, validated by
   one shared zod schema everywhere. There's also an MCP server (`lorre-blocks-mcp`) that
   wraps the CLI's JSON contract.

Live registry: **https://lorre-blocks.vercel.app** — serves `/r/index.json`,
`/r/manifest.json`, `/r/<name>.json`, `/r/themes/<theme>.json`, `/r/tokens/<theme>.json`.
GitHub: **odama-dev/lorre-blocks**. Currently ~126 registry items, CLI `0.8.0`, MCP `0.2.0`.

## 2. Repo layout — one monorepo, two shippable things

pnpm workspaces. Node **>= 22.13** required (pnpm 11.x crashes on Node 20), pnpm `11.10.0`.

```
apps/
  www/          # Next.js docs site — ALSO the registry host (serves /r/*.json)  [private]
packages/
  tokens/       # @lorre-blocks/tokens — the pure-TS token engine + theme definitions [private]
  registry/     # @lorre-blocks/registry — component source of truth + registry.ts     [private]
  cli/          # lorre-blocks — THE PUBLISHED CLI                              [public on npm]
  mcp/          # lorre-blocks-mcp — MCP server wrapping the CLI                [public on npm]
docs/           # PLAN.md (roadmap) + PROGRESS.md (session log) + phase design docs
lorre.md        # the design-system rules — when this and old habits disagree, this wins
```

**The two halves that actually ship:**

| | **A. The docs site** | **B. The CLI (+ engine + registry)** |
|---|---|---|
| Code | `apps/www` | `packages/cli`, `packages/mcp`, `packages/registry`, `packages/tokens` |
| Ships to | Vercel → lorre-blocks.vercel.app | npm → `lorre-blocks`, `lorre-blocks-mcp` |
| Released by | **merging a PR to `master`** (owner only) | GitHub Actions on push to `master` |
| Your freedom | **PR required — see §3** | **Yours to drive — see §4** |

They are coupled in one direction worth knowing: `apps/www/public/r/` is **gitignored** and
regenerated by www's `prebuild`. So registry/token changes only reach the *live* registry on
the next www deploy — i.e. a merged PR.

## 3. Track A — the docs site: **it must go through a PR**

**This is not a style preference, it's a hard constraint.** The Vercel project lives on the
`odama-studios-projects` team on a **Hobby (free) plan**, which blocks *collaborators* from
deploying a private repo. Ilyas (`zukazine`) is a collaborator, not the owner. A push or a
token-based deploy from a collaborator just hangs on a "Blocked" deployment.

The only thing Vercel accepts is its **native git integration firing on a merge by the
owner**. So:

> **Any change touching `apps/www` → feature branch → open a PR → the owner merges it.**
> The merge makes the owner the deployer, and the deploy goes through.

Do **not** try to work around this. Both workarounds have already been tried and reverted
(commit `c501bab`): a CI token-deploy, and a `vercel.json` that disables the git integration.
Don't re-add either.

Two more things so you don't get misled:

- A PR's **"Vercel" check may show FAILURE** — that's an artifact of the Hobby-plan
  collaborator invite, not a real deploy failure. Ignore it; CI is the check that matters.
- When verifying a change is live in production, **bust the edge cache** with a query param
  (`?v=2`) — stale CDN responses have fooled us before.

### The stacked-PR trap (this has cost us twice — please read)

The owner merges fast, bottom-up. GitHub only auto-retargets a stacked PR when its base
branch is **deleted on merge** — which isn't enabled here. Twice, a stack of PRs was each
merged *into its own base branch* seconds after the bottom one landed on master, so **master
never received the upper commits** and production 404'd. The recovery both times was an
extra "carry the whole remaining delta" PR (#40 was one).

**Therefore: prefer one branch per chunk of work, targeting `master` directly.** If you must
stack, wait for each merge to land before opening the next, and retarget the child to
`master` the moment its base merges. (Or ask the owner to enable "Automatically delete head
branches" in repo settings — that fixes it permanently.)

## 4. Track B — the CLI: **yours to drive**

The npm token is already configured. `NPM_TOKEN` is a repo secret in GitHub (an npm
*Automation* token, so it bypasses 2FA), and `.github/workflows/release.yml` runs
[changesets](https://github.com/changesets/changesets) on every push to `master`. Nothing
manual, no `npm login`, no browser 2FA prompt.

**The release loop:**

```bash
pnpm changeset        # describe the change, pick the semver bump → writes .changeset/*.md
# commit that file along with your code, open the PR, get it merged to master
```

Then, automatically:

1. `release.yml` sees the changeset and opens a **"Version Packages" PR** (bumps versions,
   writes CHANGELOG).
2. When **that** PR is merged, the workflow builds and **publishes to npm**.

So publishing a CLI release = two merges. Both need the owner today, because the auto-mode
classifier here blocks direct `git push` to master — route CLI changes through a PR too. But
the *mechanism* is fully wired: you never touch npm credentials.

**One manual step that is easy to forget:** the version string in
`packages/cli/src/index.ts` (`.version("0.8.0")`, line ~25) is **bumped by hand** per
release. Changesets does not touch it. Bump it in the same PR as your changeset.

Also note: only `lorre-blocks` and `lorre-blocks-mcp` publish. `www` and
`@lorre-blocks/registry` are in the changesets `ignore` list; `@lorre-blocks/tokens` is
private and gets **bundled into the CLI by tsup** (~631 KB) so theme generation works
offline — that's why the engine must stay dependency-free.

## 5. Getting set up

```bash
pnpm install
pnpm build:registry      # generates apps/www/public/r/*.json AND packages/registry/src/styles/theme.css
pnpm dev:www             # docs site on http://localhost:3000
pnpm typecheck           # all workspaces
pnpm test                # ~404 tests across cli / tokens / www render smokes
pnpm build:cli
```

`pnpm build:registry` is **not optional** before committing token changes: `theme.css` is
generated and tracked, and CI has a `git diff --exit-code` drift guard that fails the build
if you changed tokens without rebuilding.

There is a repo skill at `.claude/skills/verify/SKILL.md` with the full end-to-end
verification recipe — production build, Playwright driving of the real theme switcher, and a
fresh-consumer CLI e2e run against a local registry. Use it before claiming a change works.

| PR | Branch | Base at merge | Reached `master`? |
|---|---|---|---|
| **#47** | `feat/odama-theme` | `master` | ✅ yes |
| **#48** | `feat/odama-default-button-input` | **#47's branch** | ❌ no |

**Recovered by the PR that carries this file** — `feat/odama-docs-core` → `master`, carrying
both missing commits. Same recovery pattern as PR #40 in Phase 7.

> This is the **third** time this has happened. Please treat §3's advice as a hard rule, not
> a suggestion: **one branch per chunk, targeted at `master`.** If a stack is unavoidable,
> wait for each merge to land before opening the next. The real fix is for the owner to
> enable "Automatically delete head branches" in repo settings — GitHub then auto-retargets
> children and the trap disappears.

Note that #48/#49 straddled both tracks (they touch `packages/*` *and* `apps/www`), so they
followed the PR rule regardless.

## 7. House rules (from `lorre.md` — read the full file)

1. **Semantic tokens only.** No hardcoded colors, radii, shadows, or font sizes in
   components. Raw scale steps (`bg-accent-9`, `text-neutral-11`) are allowed only when no
   semantic alias genuinely fits.
2. **Theme = token values, never component code.** See §1.
3. **Never hand-edit generated files** — `packages/registry/src/styles/theme.css` and
   anything under `apps/www/public/r/`. Change the theme definition in
   `packages/tokens/src/themes/` and rebuild.
4. **Component tokens for the key set only** — `button`, `input` (+textarea/select trigger),
   `card`, `panel` (dialog/alert-dialog/sheet **only** — popovers and dropdowns deliberately
   keep their own radius), `badge`, `tabs`, `control` (checkbox/radio), `tooltip`. These
   consume `--<component>-<key>` vars. Everything else uses global semantic tokens.
5. **Append a `docs/PROGRESS.md` entry every working session** (newest first): decisions,
   what shipped, what's verified, what's next. This log is how the next person — human or
   agent — picks up. Please keep it up.
6. **Every registry item is classified** (`source`, `category`, `themes`, `tokenType`,
   `tags`, `license`) and validated at build time. Ported code keeps its origin `source` and
   **must** carry its license. Anything written from scratch — including AlignUI-inspired
   rewrites — is `source: "lorre"`. **AlignUI is rewrite-only: never copy its code**, its
   license is unclear.

### Adding a component

1. Source at `packages/registry/src/ui/<name>.tsx` (use `@/lib/utils`, `@/components/ui/*`
   import conventions).
2. Register in `packages/registry/registry.ts` — deps stay **bare names**; the version range
   lives in `packages/registry/package.json` and the build resolves it (build fails on an
   undeclared dep).
3. Optional demo page under `apps/www/app/docs/components/<name>/`.
4. `pnpm build:registry`.

Sidebar, search, llms.txt and docs pages all derive from the registry — a new item only
needs a demo, never manual wiring.

## 8. Gotchas that have actually bitten us

- **Node 20 fails install** with `ERR_UNKNOWN_BUILTIN_MODULE node:sqlite` — pnpm 11 needs
  Node >= 22.13. CI pins `node-version: 22`.
- **Windows:** run CLI `init`/`add` in the **foreground** — the npm-install step hangs as a
  nested background process.
- **Windows/CRLF:** scripted appends to `registry.ts` silently no-op on CRLF files. Verify
  the manifest's `itemCount` after a scripted edit, not the script's own output.
- `pnpm --filter www start -- -p 3100` fails; use `PORT=3100 pnpm --filter www start`.
  Killing that task can orphan the child `next start` process holding the port — find it
  with `netstat -ano | grep :3100`.
- **Theme switching in tests must go through the real switcher UI.** It fetches
  `/r/themes/<name>.json` and installs a `#lorre-theme-override` style tag; setting
  localStorage alone does **not** restyle non-basic themes.
- **`@theme inline` bakes font stacks into utilities at build time** — that's why the Theme
  Studio emits an explicit `body { font-family }` rule. The old runtime switcher never
  actually changed fonts.
- **`.dark` must re-declare every semantic var.** Custom properties resolve `var()` on the
  declaring element (`:root`), so a partial `.dark` block inherits resolved *light* values.
- A www demo importing an npm package directly needs that package in `apps/www/package.json`
  too — registry-transitive deps don't resolve from www under pnpm's strict node_modules.
- `plan.json`'s items key is **`add`**, not `items`.
- **Vercel's status check showing FAILURE on a PR is usually noise** (§3).
